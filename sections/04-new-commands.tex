\section{New or Enhanced PIV Commands}

This section introduces commands defined exclusively for the OSDP 3.0 Enhanced PIV profile.

Unless specified otherwise, each multi-part command or reply defined in this section places
\emph{MpSizeTotal}, \emph{MpOffset}, and \emph{MpFragmentSize}, in that order, immediately
after \emph{CMND}. Each field is a two-byte unsigned integer encoded least-significant byte
first. The bytes following \emph{MpFragmentSize} are a fragment of the logical message data:
\emph{MpSizeTotal} is the complete logical-data length, \emph{MpOffset} is the zero-based
position of the fragment, and \emph{MpFragmentSize} is the exact number of fragment bytes in
the current message. The receiver \textbf{SHALL} apply the OSDP multi-part sequencing and bounds
rules and reassemble the complete logical data before interpreting command-specific fields.
Fixed fields shown after the multi-part fields in a packet table occur at their stated position
in the reassembled data and are not repeated in every fragment. The separate
\texttt{osdp\_FILETRANSFER} framing remains unchanged.

\subsection{PIV Put Data (osdp\_PIVPUTDATA)}

The \texttt{osdp\_PIVPUTDATA} command (command code \code{0xA8}) instructs the PD to deliver an ISO~7816-4 \texttt{PUT DATA} operation to the credential. The ACU \textbf{SHALL} construct the payload as a complete BER-TLV object, including the desired outer tag (\code{0x7E} for the Discovery Object, \code{0x7F61} for a BIT Group Template, \code{0x5C}/\code{0x53} sequences for other data objects, and so on). The PD \textbf{SHALL} forward the payload to the credential using \texttt{CLA = 0x00}, \texttt{INS = 0xDB}, \texttt{P1 = 0x3F}, and \texttt{P2 = 0xFF}. If credential Secure Messaging (SM) is established, the PD \textbf{SHALL} use the established SM context and adjust the \texttt{CLA} accordingly. Chained APDUs \textbf{SHALL} be generated by the PD when the payload exceeds a single-card APDU.

\input{tables/osdp-pivputdata}

\paragraph{Responses} PIV PUT DATA requires the contact interface, including
when SM is established. On contactless, the PD \textbf{SHALL} terminate the
request without sending PUT DATA to the credential and return
\texttt{osdp\_PIVERROR} \code{0x1023} (security conditions not satisfied).
A successful write is acknowledged with \texttt{osdp\_ACK}.
If the PD does not implement the command, the PD \textbf{SHALL} return
\texttt{osdp\_NAK} function-not-supported. For a credential-side failure, the PD
\textbf{SHALL} report \texttt{osdp\_PIVERROR}, either immediately or on a
subsequent \texttt{osdp\_POLL}. The applicable codes are \code{0x1020}
(function not supported by credential), \code{0x1021} (insufficient PD buffer
space), \code{0x1022} (insufficient credential storage), \code{0x1023}
(security conditions not satisfied), and \code{0x1026} (credential absent or
removed). The status-word rules in Subsection~\ref{sec:piverror} apply.

\subsection{PIV Application Select (osdp\_PIVSELECT)}

The \texttt{osdp\_PIVSELECT} command (command code \code{0xB0}, tentative) instructs the PD to select the application identified by the supplied Application Identifier (AID) on the currently active credential. The command provides an OSDP-native selector for ISO/IEC~7816-4 \texttt{SELECT by DF name}; it is not a raw APDU tunnel and does not expose APDU header bytes to the ACU. PDs \textbf{SHALL} advertise support via Function Code~12 bit~\code{0x04} (Enhanced PIV) before controllers attempt to use this command.

\input{tables/osdp-pivselect}

The PD \textbf{SHALL} issue \texttt{SELECT} with \texttt{CLA = 0x00},
\texttt{INS = 0xA4}, \texttt{P1 = 0x04}, \texttt{P2 = 0x00},
\texttt{Lc = AID Length}, \texttt{Data = AID}, and \texttt{Le = 0x00}.
The PD \textbf{SHALL} request the normal application property template over the interface selected
by the current PIV mode. A selection within an established SM context follows
the shared transport rules in Subsection~\ref{sec:credential-sm-flow}.
When the credential selects a different application, the PD \textbf{SHALL} clear the
previous application's SM session, VCI status, pairing code, cached PIN,
PIN-verification status, and application information. This prevents the PD from
carrying security state from one application into another.
Selecting the PIV application when a credential is first presented preserves a PIN
collected before presentation. Selecting the same PIV application again preserves
its SM session and PIN-verification status. If the credential rejects SELECT, the PD
keeps the current application and its state.

The \emph{AID Length} field \textbf{SHALL} be in the ISO/IEC~7816 application identifier range of 5 to 16 bytes. If the payload is malformed, the AID length is outside that range, or any reserved selection flag is nonzero, the PD \textbf{SHALL} report \texttt{osdp\_PIVERROR} \code{0x0005} (invalid parameter). A successful selection is acknowledged with \texttt{osdp\_ACK}; after success, subsequent PIV commands operate against the selected application until the credential is removed, a new \texttt{osdp\_PIVSELECT} succeeds, or \texttt{osdp\_PIVMODE} changes the operating context. The PD \textbf{SHALL} update the selected AID reported by \texttt{osdp\_CARDSTATUSR}; if the credential returns an FCI template containing tag \code{0x4F}, that value \textbf{SHALL} be reported, otherwise the PD \textbf{SHALL} report the requested AID.

If the PD does not implement the command, the PD \textbf{SHALL} return
\texttt{osdp\_NAK} function-not-supported. Credential-side failures
\textbf{SHALL} be reported using \texttt{osdp\_PIVERROR}: \code{0x1020}
(application selection unsupported), \code{0x1023} (security conditions not
satisfied), \code{0x1024} (requested AID absent), or \code{0x1026} (credential
absent or removed). The status-word rules in Subsection~\ref{sec:piverror} apply.

\subsection{Card Status (osdp\_CARDSTATUS)}

The \texttt{osdp\_CARDSTATUS} command (command code \code{0xA9}, tentative) requests the current credential context from the PD. PDs \textbf{SHALL} advertise support via Function Code~12 bit~\code{0x04} (Enhanced PIV) before controllers attempt to use this command. The payload selects standard credential status or SM diagnostics.

\input{tables/osdp-cardstatus}

PDs \textbf{SHALL} return \texttt{osdp\_NAK} function-not-supported when the command itself is not implemented. If the requested status type is not supported or the payload is malformed, PDs \textbf{SHALL} report the condition via \texttt{osdp\_PIVERROR} (for example \code{0x0005} (invalid parameter)) on a subsequent \texttt{osdp\_POLL}.

\subsection{Card Status Reply (osdp\_CARDSTATUSR)}

Every \texttt{osdp\_CARDSTATUSR} reply \textbf{SHALL} include Status Type
immediately after the reply code. Type \code{0x01} selects the standard
credential status fields below. Type \code{0x02} selects the diagnostic
multi-part layout in Subsection~\ref{sec:sm-diagnostics}.
The ACU \textbf{SHALL} select the reply layout from this byte and verify
that the type matches the pending request. An unknown or mismatched type
\textbf{SHALL} be treated as an invalid reply; the ACU discards the reply
and any partially reassembled record. The ACU can cancel the pending
operation with ABORT and issue a new request.

The PD accepts \texttt{osdp\_CARDSTATUS} Type \code{0x01} with \texttt{osdp\_ACK} and returns
\texttt{osdp\_CARDSTATUSR} on a subsequent \texttt{osdp\_POLL} after the current
credential preparation completes. The PD \textbf{SHALL} use a finite, documented
preparation timeout. If SM is established and the credential requires a pairing code,
the PD reports that state so the ACU can supply the code. The ACU \textbf{SHALL}
interpret the following combination as pairing required: Detected Credential
Type \code{0x02}, Credential Security Status \code{0x02}, and an available
PIN Usage Policy whose first byte has mask \code{0x08} set and mask
\code{0x04} clear. Security Status \code{0x02} alone indicates SM without VCI;
contact SM requires no pairing. While status is pending,
the ACU sends only \texttt{osdp\_POLL} or \texttt{osdp\_ABORT}.

\texttt{osdp\_CARDSTATUSR} also completes an accepted
\texttt{osdp\_PIVXMITPAIRING} command, using Status Type \code{0x01}.
Controllers continue to use \texttt{osdp\_RAW} for ordinary card-data indications.
Whenever credential SM is established, the status reply reports the CVC IIN and
the loaded anchor IIN, including for contact SM. The values match for direct
verification and differ when an Intermediate CVC is used. The \emph{SM Trust
Anchor ID} identifies the corresponding \texttt{osdp\_PIVVCITASTATUSR} inventory
entry, whose IIN matches \emph{SM Anchor IIN}.

\input{tables/osdp-cardstatusr}

Each accepted Type \code{0x01} status request \textbf{SHALL} complete with either
\texttt{osdp\_CARDSTATUSR} or \texttt{osdp\_PIVERROR}. If a failed SM security
check has blocked credential operations, the PD \textbf{SHALL} terminate a
Status Type \code{0x01} request without sending further commands or data to
the credential. The PD \textbf{SHALL} return \texttt{osdp\_PIVERROR}
\code{0x1023} (credential security conditions not satisfied) on the next poll.
Otherwise, the standard status reply includes the
selected AID when available and any previously read PIN Usage Policy bytes
from Discovery Object tag \code{0x5F2F}, unchanged. The status request itself
requires no Discovery Object read. The PD reports \code{0xFFFF} when the policy
is unavailable. Security status reports the result of credential preparation.
With no credential present, the PD reports credential type and security status zero,
AID length zero, and PIN
Usage Policy \code{0xFFFF}. Removal during preparation returns
\texttt{osdp\_PIVERROR} \code{0x1026} (credential absent or removed). A preparation
timeout returns \texttt{osdp\_PIVERROR} \code{0x0002} (smart-card timeout).
\texttt{osdp\_ABORT} cancels the request with \texttt{osdp\_ACK} and clears its
pending completion reply.

\subsection{PIV Secure PIN Entry (osdp\_PIVSPE)}

The \texttt{osdp\_PIVSPE} command (command code \code{0xAA}, tentative) controls
Secure PIN Entry for the Enhanced PIV profile. A PD \textbf{SHALL} advertise both
Function Code~12 bit~\code{0x04} (Enhanced PIV) and Function Code~15 Secure PIN
Entry support before an ACU uses this command. The OSDP~2.2
\texttt{osdp\_XWR} Mode-01 SPE command and \texttt{osdp\_PR01SPER} reply remain
unchanged.

The ACU is responsible for conveying a clear indication that PIN entry is in
progress. While the PD is acquiring a PIN, it \textbf{SHALL} suppress
\texttt{osdp\_KEYPAD} reports so that no PIN digit is sent to the ACU.

\input{tables/osdp-pivspe}

\input{tables/osdp-pivspe-modes}

\input{tables/osdp-pivspe-flags}

Modes are enumerated values. Modes \code{0x02} and \code{0x03} submit the
cached PIN using PIV \texttt{VERIFY}. Mode \code{0x02} requires established
VCI; Mode \code{0x03} uses the credential interface selected by the active
PIV mode. Mode \code{0x01} acquires the PIN and uses the selected interface.
The ACU selects Mode \code{0x02} to require VCI explicitly, or Mode
\code{0x03} to permit verification on either the selected contact interface
or established VCI. Both modes have the same behavior on contactless.
Mode \code{0x02} returns \code{0x09} (VCI not established) on contact,
even when contact SM is established; Mode \code{0x03} permits that workflow.
When credential SM is established, the PD \textbf{SHALL} use that session
for Modes \code{0x01}-\code{0x03} and \code{0x06}.
Contactless PIN verification requires VCI. Contact PIN verification may use
the contact interface without SM. Mode \code{0x04} requires a \emph{Cache Validity} from
\code{0x0001} through \code{0xFFFF}. All other modes \textbf{SHALL} transmit
\code{0x0000} in that field. The PD \textbf{SHALL NOT} transmit an entered or
cached PIN to the ACU.

A zero \emph{Start Timeout} or \emph{Inter-key Timeout} selects the PD's
documented default. Each default \textbf{SHALL} be from 1 through 255 seconds.
Nonzero values specify seconds and \textbf{SHALL} override the corresponding
default. The ACU should supply explicit values when deployment or test
requirements specify the timing. Fields that do not apply to a selected mode
\textbf{SHALL} be transmitted as zero.

Only one \texttt{osdp\_PIVSPE} operation may be outstanding. Modes
\code{0x01}-\code{0x04} and \code{0x06} each initiate one operation. The PD returns
\texttt{osdp\_ACK} when it accepts the request, then returns one
\texttt{osdp\_PIVSPER} in response to a later \texttt{osdp\_POLL}. While such
an operation is pending, the ACU \textbf{SHALL} send only
\texttt{osdp\_POLL}, Mode \code{0x05}, or \texttt{osdp\_ABORT}. Returning
\texttt{osdp\_PIVSPER} ends the operation unconditionally, including after a
PIN mismatch.

Mode \code{0x00} returns \texttt{osdp\_PIVSPER} directly. It reports only
persistent PIN state; it does not report transient active or waiting states.
An ACU recovering from an interrupted session first uses Mode \code{0x05} or
\texttt{osdp\_ABORT}, then queries Mode \code{0x00}. Mode \code{0x06} is
accepted with \texttt{osdp\_ACK}; the PD reads the present credential without
performing PIN verification and returns the count in a subsequent
\texttt{osdp\_PIVSPER}. This query \textbf{SHALL NOT} decrement the credential
retry counter. Auto Execute does not make the count available without a
present credential. The PD \textbf{SHALL} return \code{0xFF} (attempts
unavailable) when the credential is absent or the active interface and
security context do not permit the query. Contactless queries require VCI.

Mode \code{0x05} is idempotent. It aborts active or partial PIN entry, clears
the cached PIN, and completes with \texttt{osdp\_ACK}; the PD \textbf{SHALL
NOT} send a later \texttt{osdp\_PIVSPER} for the canceled operation.
\texttt{osdp\_ABORT} cancels active or partial PIN entry but preserves a cache
that was completed before the active operation.

A successful verification \textbf{SHALL} preserve the cached PIN until
expiration or a clearing event. A later explicit verification request may
reuse that PIN. The PD \textbf{SHALL} clear the cache on Mode \code{0x05},
PIN mismatch, PD reset, loss of the OSDP Secure Channel, or a
change to the PIV mode or a change from one selected application to another.
Initial application selection and initial SM establishment \textbf{SHALL}
preserve a PIN cached before credential presentation. Credential removal also clears
it unless flag \code{0x01} was supplied with Mode \code{0x04}. Loss of credential
SM while the credential remains present clears the cache. Removal follows the
removal flag even when it also ends SM. PIN-verified
status is bound to the current credential, selected application, interface,
and credential security context. The PD \textbf{SHALL} clear that status on
credential removal or reset, a change to the selected application, interface
change, PIV mode change, or loss of credential SM or VCI, and \textbf{SHALL NOT} infer it only
from an earlier successful reply.

\input{sections/05-pin-cache-lifecycle}

Flag \code{0x02} arms the verification selected by Mode \code{0x01},
\code{0x02}, or \code{0x03} to execute when a credential is presented. It
\textbf{SHALL} be zero for Modes \code{0x00}, \code{0x04}, \code{0x05}, and
\code{0x06}. A cached auto-execute workflow first acquires the PIN with Mode
\code{0x04}, then selects normal or VCI verification with Mode \code{0x03} or
\code{0x02} and flag \code{0x02}.

Without Auto Execute, verification begins after acceptance with the credential
and required security context already available. An absent credential returns
\emph{Result} \code{0x04} (credential absent or removed). When Mode \code{0x02}
is requested or verification uses contactless, missing VCI returns
\code{0x09} (VCI not established). The ACU completes any required pairing before
requesting verification.

With Auto Execute, the PD waits for presentation, completes credential preparation
(Subsection~\ref{sec:credential-sm-flow}), and attempts verification once. If
preparation requires a pairing code, the PD completes the SPE operation with
\code{0x09} (VCI not established). If the cached PIN expires while waiting,
the PD completes with \code{0x0A} (no cached PIN). A failed verification completes
the operation without an automatic retry. The ACU may then perform setup and
start a new SPE operation.

The ACU \textbf{SHALL} disable PIV Auto before arming SPE Auto Execute. A request
to arm SPE while PIV Auto is enabled receives \texttt{osdp\_NAK} \code{0x09}
(unable to process command). This ensures that only one operation starts credential
preparation and PIN verification when the credential is presented.

The PD \textbf{SHALL} reject an unsupported command with \texttt{osdp\_NAK}
\code{0x03}, an incorrect command length with \texttt{osdp\_NAK} \code{0x02},
and an invalid mode, reserved bit, or field combination with
\texttt{osdp\_NAK} \code{0x09}. Accepted credential-side outcomes are reported
through \texttt{osdp\_PIVSPER}, not \texttt{osdp\_PIVERROR}.

\subsection{PIV Biometric Match (osdp\_PIVBIOMATCH)}

The \texttt{osdp\_PIVBIOMATCH} command (command code \code{0xAB}, tentative) instructs the PD to acquire a live sample and compare it to the specified biometric template from the active application. Depending on the \emph{Match Mode}, the comparison occurs either on the credential (on-card match) or within the PD (off-card match).

\input{tables/osdp-pivbiomatch}

\input{tables/osdp-pivbiomatch-types}

For contactless on-card comparison, the PD \textbf{SHALL} use credential SM.
This operation can proceed with SM established and VCI absent;
pairing and VCI are required only when the credential's access conditions
require them. Other biometric operations use established SM when present.

Controllers set \emph{Match Mode} to select off-card or on-card comparison. Off-card flows require the PD to retrieve the appropriate template and, where applicable (e.g., TWIC contactless), to have a valid privacy key loaded via \texttt{osdp\_PIVLOADTPK}. On-card flows require the credential to support OCC. If the PD does not implement the command, it \textbf{SHALL} return \texttt{osdp\_NAK} function-not-supported. Credential-side match outcomes (for example PIN verification required or credential removal during operation) \textbf{SHALL} be reported in the subsequent \texttt{osdp\_PIVBIOMATCHR} result code per Table~\ref{tab:pivbiomatch-results}. Conditions that prevent the command from being attempted (for example unsupported credential function, missing VCI when required, or invalid command parameters) \textbf{MAY} be reported via \texttt{osdp\_PIVERROR} on a subsequent \texttt{osdp\_POLL}.

\subsection{PIV Biometric Match Reply (osdp\_PIVBIOMATCHR)}

After \texttt{osdp\_PIVBIOMATCH} completes, the PD reports the result as a poll response using reply code \code{0x87} (tentative).

\input{tables/osdp-pivbiomatchr}

When \emph{Result} is \code{0x00} (off-card match success), the PD \textbf{SHALL} include the 32-byte SHA-256 hash of the biometric template tag \code{0xBC} data field in the reply. For on-card match success (\emph{Result} \code{0x09}) and for all failure result codes, the PD \textbf{SHALL} omit the hash field; ACUs \textbf{SHALL NOT} rely on a hash received alongside any result other than \code{0x00}.

Off-card biometric comparison demonstrates only that the live sample matched template data presented to the PD. Because off-card biometric objects can be copied or duplicated, an off-card biometric match does not by itself prove authenticity of the credential. On-card biometric comparison is a credential-controlled assertion; the biometric object may be attacker controlled and the PD does not receive the template data being matched. To obtain cryptographic proof associated with an on-card biometric success, the ACU \textbf{SHALL} perform an additional authentication using an appropriately verified credential key after the successful on-card comparison.

\subsection{TWIC Privacy Key Load (osdp\_PIVLOADTPK)}

The \texttt{osdp\_PIVLOADTPK} command (command code \code{0xAC}, tentative) instructs the PD to cache a TWIC Privacy Key (TPK) for use with subsequent biometric operations against a TWIC credential. Function Code~14 is the biometric-support compliance byte; before using this command, controllers \textbf{SHOULD} verify that Function Code~14 advertises the OSDP~3.0 biometric command set and the relevant biometric modality bits for the intended TWIC operation.

\input{tables/osdp-loadtpk}

Controllers set \emph{Cache Timeout} to define how long (in seconds) the PD may retain the key. A value of \code{0x00} clears any cached TPK immediately. Values \code{0x01}-\code{0xFF} allow caching for up to 255 seconds. Bit~0 of \emph{Control Flags} directs the PD to clear the cached TPK when the credential is removed; all other bits are reserved and \textbf{SHALL} be transmitted as zero. If the PD does not support TWIC TPK caching it \textbf{SHALL} return \texttt{osdp\_NAK} function-not-supported. Invalid payloads (for example reserved bits set) \textbf{SHALL} elicit \texttt{osdp\_PIVERROR} \code{0x0005} (invalid parameter).

\subsection{PIV VCI Pairing Code Transmit (osdp\_PIVXMITPAIRING)}

The \texttt{osdp\_PIVXMITPAIRING} command (command code \code{0xAD}, tentative)
submits an eight-digit pairing code to the selected contactless PIV application
over established credential SM. The ACU \textbf{SHALL} send it over OSDP Secure
Channel~2.0. Credential SM, PIVMODE flag \code{0x02}, and credential support
for VCI are prerequisites.

\input{tables/osdp-xmitpairing}

The pairing code contains eight ASCII digits (\texttt{'0'}-\texttt{'9'}).
The PD accepts a valid request with \texttt{osdp\_ACK}. When pairing is required,
the PD submits the code using PIV \texttt{VERIFY}, reference \code{0x98}, protected
by the established SM context. Success completes with \texttt{osdp\_CARDSTATUSR}
on a later \texttt{osdp\_POLL}, reporting security status \code{0x01} (SM and VCI).
If VCI is already available, the PD completes with the same status reply without
submitting the code again.

An accepted operation completes with \texttt{osdp\_PIVERROR} on failure:
\code{0x0005} (invalid parameter) for malformed digits or no selected PIV
application, \code{0x1023} (security conditions not satisfied) for missing SM,
disabled SM/VCI preparation, the wrong interface, or a rejected pairing code,
\code{0x1020} (function not supported by credential) when VCI is unsupported,
\code{0x1026} (credential absent or removed), or \code{0x0002} (smart-card timeout).
The PD includes the credential's failure status word as specified in
Subsection~\ref{sec:piverror}. If a submitted pairing VERIFY times out without
a confirmed result, the PD \textbf{SHALL} end SM, clear dependent VCI,
PIN-verification, and cached-PIN state, and require an explicit preparation
restart before further credential data or authentication commands.
The PD \textbf{SHALL} return \code{0x0002} (smart-card timeout) without SW1/SW2
and \textbf{SHALL NOT} retry VERIFY automatically.
While pairing is pending,
the ACU sends only \texttt{osdp\_POLL} or \texttt{osdp\_ABORT}. Competing commands
receive \texttt{osdp\_NAK} \code{0x09} (unable to process command).

The PD \textbf{SHALL} clear the transient pairing code on completion, failure,
cancellation, or loss of its credential context. \texttt{osdp\_ABORT} completes
with \texttt{osdp\_ACK} and clears the pending completion. For an OSDP
retransmission, the PD \textbf{SHALL} replay the previous reply without
resubmitting the pairing code.

\paragraph{OSDP security preconditions}
Trust-anchor load/status, pairing-code transmit, credential SM establishment,
and PIV operations that depend on SM or VCI \textbf{SHALL} require OSDP Secure
Channel~2.0 between the ACU and PD with deployment-specific keys. OSDP Secure
Channel protects the management commands and their results. Credential SM protects
the PD-to-card exchange. A security-precondition failure returns
\texttt{osdp\_PIVERROR} \code{0x0006} (secure channel required) where supported;
otherwise the command's existing failure reply applies.

\subsection{Set PIV Mode (osdp\_PIVMODE)}\label{sec:pivmode}

The \texttt{osdp\_PIVMODE} command (command code \code{0xAE}, tentative) defines the operating context for PIV, TWIC, and related credential transactions. OSDP~3.0 replaces the OSDP~2.2 “Application + AID” fields with a configuration payload that includes a required Global Interface Mask byte, PIV Auto challenge parameters when autonomous operation is enabled, and a TLV list of configuration descriptors so controllers can specify multiple application profiles, preferred interfaces, and optional Application Identifiers. PDs \textbf{SHALL} advertise support via Function Code~12 bit~\code{0x04} (Enhanced PIV).

\input{tables/osdp-pivmode}

The \emph{PIV Mode Flags} byte enables autonomous operation and credential SM/VCI
preparation (Table~\ref{tab:pivmode-flags}). Bits not listed remain reserved and
\textbf{SHALL} be transmitted as zero.

\input{tables/osdp-pivmode-flags}

Global and per-entry interface masks use the bit positions in Table~\ref{tab:pivmode-interfaces}; the Global Interface Mask bounds the interfaces a PD may use when processing all configuration entries.

\input{tables/osdp-pivmode-interfaces}

The reassembled configuration data begins at \emph{MpOffset}~\code{0x0000} with
\emph{PIV Mode Flags}, followed by the configuration count (1-32) and the required Global
Interface Mask byte. \emph{MpSizeTotal} counts all configuration data from \emph{PIV Mode
Flags} through the final TLV byte. If and only if PIV Auto is enabled in \emph{PIV Mode Flags},
the Global Interface Mask is followed by the Series Counter, Sequence Counter, and fixed
32-byte Supplemental Entropy field before the TLV list. When PIV Auto is not enabled, those
three conditional fields are absent and the TLV list begins immediately after the Global
Interface Mask. Each configuration appears as a TLV:

The configuration count \textbf{SHALL} equal the number of complete Configuration Entry
TLVs in the reassembled payload. Consequently, \emph{MpSizeTotal} \textbf{SHALL} be at
least eight bytes when PIV Auto is disabled and at least 48 bytes when it is enabled, and
\textbf{SHALL} equal the exact encoded length of the required header, any conditional PIV
Auto fields, and all configuration TLVs. Truncated fields, trailing bytes, or a count that
does not match the TLV sequence \textbf{SHALL} be treated as malformed configuration data.

\begin{itemize}
  \item \textbf{Global Interface Mask (required)} — One-byte mask (no tag) that limits the interfaces the PD may use for all configurations (see Table~\ref{tab:pivmode-interfaces}). A value of \code{0x00} indicates no global restriction; reserved bits \textbf{SHALL} be zero.
  \item \textbf{Configuration Entry (Tag \code{0x01})} — Contains the data-model identifier, a per-entry interface mask, the AID length, and the optional AID:
    \begin{itemize}
      \item \emph{Data Model} (\code{0x01} PIV, \code{0x02} TWIC, \code{0x03} CAC, values \code{0x04}-\code{0x7F} reserved, \code{0x80}-\code{0xFF} private use). CAC entries use the same interface and AID encoding as PIV and TWIC entries.
      \item \emph{Interface Mask} — Uses the same bit positions as the global mask (Table~\ref{tab:pivmode-interfaces}) and \textbf{SHALL NOT} assert interfaces excluded by the Global Interface Mask. A value of \code{0x00} means “any interface permitted by the global mask.”
      \item \emph{AID Length} (0-16) and \emph{AID} bytes when provided.
    \end{itemize}
\end{itemize}

PDs process configuration entries in order, applying the global mask (when present) before honouring each entry’s mask. Invalid masks, unknown data-model identifiers, or malformed TLVs \textbf{SHALL} result in \texttt{osdp\_PIVERROR} \code{0x0005} (invalid parameter). Controllers \textbf{SHALL} send the command over a secure channel where required; the PD \textbf{SHALL} return \texttt{osdp\_PIVERROR} \code{0x0006} (secure channel required) if the necessary security conditions are not satisfied. Multi-part framing errors result in \texttt{osdp\_PIVERROR} \code{0x0007} (invalid multi-part transfer). If the PD cannot cache the requested configuration set, it \textbf{SHALL} respond with \texttt{osdp\_PIVERROR} \code{0x1021} (insufficient PD memory or storage).

When PIV Auto is enabled, the PD prepares the presented credential as described
in Subsection~\ref{sec:credential-sm-flow}, derives the challenge, issues PIV
\texttt{GENERAL AUTHENTICATE}, and reports completion through
\texttt{osdp\_PIVSTATUS}. The PD \textbf{SHALL} use the configured key,
algorithm, and selected interface for that attempt. If SM is unavailable, the
PD continues that same authentication only when the credential's access rules permit
the authentication without SM, as for key \code{0x9E}. If the configured
authentication requires SM, the PD reports the SM failure. A failed signature
or cryptogram check ends the attempt even when the authentication could
otherwise proceed without SM.

PIV Auto can establish VCI when the credential permits VCI without a pairing code.
For an authentication that requires SM, the PD first checks whether SM is
established. If SM is unavailable, the PD reports Result \code{0x02} (SM failure)
with the applicable detail code. The PD then checks any VCI and PIN-verification
requirements, in that order.
If the selected authentication requires VCI and pairing is required, the PD
completes with Result \code{0x05}, Detail \code{0x01} (pairing code required).
The ACU can then begin commanded pairing. Required PIN verification that has
not been completed returns Result \code{0x05}, Detail \code{0x02} (PIN verification
required). PIV Auto performs one attempt per presentation. Keeping the same
credential presented does not restart the attempt. Removal and a new
presentation, or successful reapplication of \texttt{osdp\_PIVMODE}, starts a new
attempt. Reapplication follows the mode-change clearing rules; loading a trust
anchor alone does not restart authentication.

PIV Auto configuration \textbf{SHALL} be accepted only when OSDP Secure Channel~2.0 is active and the channel is not using a factory/default SCBK or other factory key material. A PD \textbf{SHALL} reject PIV Auto configuration or execution with \texttt{osdp\_PIVERROR} \code{0x0006} (secure channel required) when these preconditions are not met.

When bit \code{0x01} of \emph{PIV Mode Flags} enables PIV Auto, the configuration \textbf{SHALL} specify a \emph{Series Counter}, a \emph{Sequence Counter}, and a 32-byte \emph{Supplemental Entropy} field. The supplemental entropy field is fixed width and \textbf{SHALL} always be present; all zeroes are permitted for compatibility but are not recommended. The ACU \textbf{SHALL} ensure that a series counter value does not repeat for the same PD and that no sequence counter value is issued more than once within a series. One conforming implementation strategy is to maintain a monotonic series counter that increments at every ACU boot, similar to the SNMP engine boots counter, and a monotonic sequence counter for challenges issued within that boot series.

The PIV Auto challenge \textbf{SHALL} be derived from the active Secure
Channel~2.0 session key material using two KMAC256 operations. First, the PD
derives a 32-byte PIV Auto KDK with key material formed by concatenating
\code{S-ENC}, \code{S-MAC1}, and \code{S-MAC2}; empty input data; output length
32 bytes; and customization string \code{OSDP-PIV-AUTO-KDK-v1}. Second, the PD
derives the challenge digest using the PIV Auto KDK as the KMAC key, the
fixed-width template as input data, output length \code{L}, and customization
string \code{OSDP-PIV-AUTO-CHALLENGE-v1}. The fixed-width template
\textbf{SHALL} contain the series counter, sequence counter, credential
FASC-N, credential UUID, challenged PIV key reference, PIV algorithm
identifier, and the 32-byte supplemental entropy field. A successful PIV Auto
transaction \textbf{SHALL} include the credential UUID; if the UUID cannot be
read, the PD \textbf{SHALL} report PIV Auto failure instead of deriving a
success challenge with an all-zero UUID. The output length \code{L} is 32 bytes
for SHA-256 profiles and 48 bytes for SHA-384 profiles. PIV Auto challenge
derivation \textbf{SHALL NOT} use static factory keys.

\subsection{PIV Auto Status Reply (osdp\_PIVSTATUS)}

When a PIV Auto attempt completes, including a failure during preparation, the
PD reports the result as a poll response using reply code \code{0x89} (tentative).
The first \texttt{osdp\_POLL} response after completion \textbf{SHALL} contain
\texttt{osdp\_PIVSTATUS}; subsequent fragments, when required, use the same reply
and advance \emph{MpOffset} until the complete status payload is delivered.
There is no corresponding \texttt{osdp\_PIVSTATUS} request command.

Result and detail codes follow Table~\ref{tab:pivstatusr-results}. When \emph{Result} is \code{0x00}, \emph{Detail} is reserved and \textbf{SHALL} be \code{0x00}. When \emph{Result} is not \code{0x00}, the PD \textbf{SHALL} set \emph{Signed Response Length} to \code{0x0000} unless a credential response was received and is useful for ACU diagnostics.

The PD \textbf{SHALL} append SW1 followed by SW2 when a credential command
returned the failure being reported. For a verified protected reply, the PD
uses the protected status. The PD \textbf{SHALL} omit this field on success,
local failure, timeout, credential removal without a failure reply, or failure
to verify a protected reply. An earlier command's status \textbf{SHALL NOT}
be used. These are the status-word rules of Subsection~\ref{sec:piverror}.

For failure before challenge generation, the PD \textbf{SHALL} report the
configured series and sequence counters and requested key reference and
algorithm. It \textbf{SHALL} set unavailable FASC-N and UUID fields to zero and
\emph{Signed Response Length} to zero. These identity fields describe data
actually obtained from the credential. The PD \textbf{SHALL} set \emph{Detail}
to zero unless the result defines a detail value.

The reply reports the exact series and sequence counters used for the challenge, the FASC-N and UUID read from the credential, and the signed response returned by the credential. The ACU uses these fields to verify counter uniqueness, bind the response to the credential identity, and validate the signature and certificate path using ACU trust policy. A success result \textbf{SHALL} include a nonzero credential UUID. The PD \textbf{SHALL} preserve the credential's signed response bytes as returned by the PIV operation, excluding transport status words such as SW1/SW2.

If the complete signed response does not fit in one OSDP response, the PD

multi-part convention. \emph{MpSizeTotal} is the total status payload size,
\emph{MpOffset} is the zero-based offset of the fragment, and
\emph{MpFragmentSize} is the number of payload bytes carried in that fragment.
The logical status payload begins at offset zero with the fixed fields; each fragment carries
the next contiguous bytes of that payload. A fragment boundary may occur within the fixed
fields or within the signed response.

\subsection{VCI Trust Anchor Load (osdp\_PIVVCILOADTA)}

The \texttt{osdp\_PIVVCILOADTA} command (command code \code{0xAF}, tentative)
loads, replaces, or deletes a credential SM trust anchor. The existing command
name and record format apply to both contact and contactless SM. The ACU
\textbf{SHALL} validate and authorize each anchor under its deployment
certificate policy before loading it. The PD uses the loaded public key to
validate the credential's SM CVC.

\input{tables/osdp-vciloatda}

The reassembled operation data begins at \emph{MpOffset}~\code{0x0000} with a 12-byte
metadata block containing \emph{Operation}, \emph{Trust Anchor ID}, \emph{Issuer Identifier
Number}, and \emph{Anchor Length}, followed immediately by \emph{Anchor Data}. These fields
may cross fragment boundaries and are interpreted only after the complete logical data has been
reassembled. Controllers set \emph{Operation} to \code{0x00} to load or replace the anchor
identified by \emph{Trust Anchor ID}. Set \emph{Operation} to \code{0x01} with \emph{Anchor
Length}~\code{0x0000} and \emph{MpSizeTotal}~\code{0x000C} to delete the anchor. For a
delete operation, the supplied IIN \textbf{SHALL} match the IIN of the stored anchor selected
by \emph{Trust Anchor ID}; a mismatch \textbf{SHALL} be rejected with
\texttt{osdp\_PIVERROR} \code{0x0005} (invalid parameter). Inventory is
requested with \texttt{osdp\_PIVVCITASTATUS}, not with \texttt{osdp\_PIVVCILOADTA}. The
\emph{Issuer Identifier Number (IIN)} is an OSDP-defined anchor selector: it \textbf{SHALL} be
the leftmost eight bytes of the subjectKeyIdentifier from the content-signing X.509 certificate
associated with this anchor. For load/replace, this value \textbf{SHALL} match the IIN field
(tag \code{0x42}) in the VCI trust anchor record.

The \emph{Anchor Length} declares the exact size of the variable-length VCI trust anchor record.
For every operation, \emph{MpSizeTotal} \textbf{SHALL} equal \code{0x000C} plus \emph{Anchor
Length}. For an operation accepted for processing, the sum of all accepted
\emph{MpFragmentSize} values \textbf{SHALL} equal \emph{MpSizeTotal}, and no fragment
\textbf{SHALL} extend beyond \emph{MpSizeTotal}. For load
operations, the reassembled bytes following the metadata block \textbf{SHALL} contain exactly
\emph{Anchor Length} bytes. A conforming VCI trust anchor record \textbf{SHALL NOT} exceed 576
bytes (\code{0x0240}), making the maximum \emph{MpSizeTotal} \code{0x024C}. The PD
\textbf{SHALL} accept any valid record length from the minimum BER-TLV encoding through
\code{0x0240}, subject to supported-key and storage-capacity checks.

PD storage accounting for VCI trust anchors is variable-length. A PD \textbf{SHALL NOT} treat every anchor as consuming the maximum \code{0x0240} bytes unless that is the PD's documented physical allocation model. When reporting capacity, loading, replacing, or deleting anchors, the PD \textbf{SHALL} account for stored anchors by their actual \emph{Anchor Length} values and \textbf{SHALL} use the same accounting rule for both \texttt{osdp\_PIVVCITASTATUSR} \emph{Available Bytes} and \texttt{osdp\_PIVVCILOADTA} storage acceptance. A replacement operation \textbf{SHALL} be evaluated after releasing the storage occupied by the existing anchor with the same \emph{Trust Anchor ID}; if the replacement cannot be completed, the prior anchor \textbf{SHALL} remain available. A delete operation \textbf{SHALL} release the storage associated with the deleted anchor.

The VCI trust anchor record is intentionally not a NIST SP~800-73 Intermediate CVC and does not carry X.509 path-validation state. The ACU is responsible for selecting, loading, unloading, and validating the VCI anchors it permits a PD to use before the PD relies on them. The PD uses the record only as a local public-key verifier selected by IIN. The maximum record size is derived from the largest supported key case: a 550-byte RSA-4096 SubjectPublicKeyInfo plus the fixed fields above and BER-TLV length overhead. The resulting worst case is 573 bytes; this specification rounds the maximum accepted record size to 576 bytes.

\paragraph{Use during credential SM establishment}
When the PD receives the secure messaging CVC from the credential, it \textbf{SHALL} first extract the Issuer Identification Number from tag \code{0x42}. If a loaded VCI trust anchor has a matching IIN, the PD \textbf{SHALL} use that anchor's SubjectPublicKeyInfo to verify the secure messaging CVC signature. If verification succeeds, the PD may continue credential SM establishment using the public key in the secure messaging CVC.

If no loaded VCI trust anchor matches the secure messaging CVC IIN, the PD \textbf{SHALL} retrieve the Secure Messaging Certificate Signer data object (object identifier \code{0x5FC122}, container identifier \code{0x1017}) from the credential and inspect it for one Intermediate CVC (tag \code{0x7F21}). If the object is absent or no Intermediate CVC is present, validation fails. If an Intermediate CVC is present, the PD \textbf{SHALL} verify all of the following before continuing:
\begin{itemize}
  \item The secure messaging CVC IIN (tag \code{0x42}) equals the Subject Identifier (tag \code{0x5F20}) in the Intermediate CVC.
  \item The Intermediate CVC Role Identifier (tag \code{0x5F4C}) is \code{0x12}.
  \item A loaded VCI trust anchor exists whose IIN equals the Intermediate CVC IIN (tag \code{0x42}).
  \item The Intermediate CVC signature verifies using the matching VCI trust anchor public key.
  \item The secure messaging CVC signature verifies using the public key carried in the Intermediate CVC.
\end{itemize}

The PD validates only the CVC chain needed for credential SM establishment: either the loaded trust anchor directly verifies the secure messaging CVC, or the loaded trust anchor verifies the Intermediate CVC that then verifies the secure messaging CVC. The PD \textbf{SHALL NOT} establish credential SM unless this CVC validation succeeds. The PD \textbf{SHALL NOT} perform full X.509 path validation, validity-period evaluation, certificate-policy evaluation, or revocation processing for VCI trust anchors; those checks are completed by the ACU before loading anchors and again as an acceptance policy after credential SM state is reported.

An absent signer object, an absent intermediate CVC, or the absence of a
matching loaded anchor leaves the PD without a matching trust path. The PD
reports SM Detail \code{0x02} for that condition. A malformed CVC, incorrect
role or linkage, or failed signature check reports Detail \code{0x03} and
blocks credential operations. These distinctions apply to both PIV Auto
results and SM diagnostics.

\paragraph{ACU acceptance of credential SM}
After receiving \texttt{osdp\_CARDSTATUSR} with credential SM established, the ACU \textbf{SHALL} validate the content-signing certificate corresponding to the reported \emph{SM Anchor IIN} before treating the credential SM session as accepted for the deployment. This validation is an additional ACU acceptance check and does not replace the PD's required CVC validation during credential SM establishment. The ACU \textbf{SHALL} perform all of the following:
\begin{itemize}
  \item Obtain the content-signing X.509 certificate. If the ACU does not already possess a cached copy whose subjectKeyIdentifier leftmost-eight-bytes equals the \emph{SM Anchor IIN}, the ACU \textbf{SHALL} use \texttt{osdp\_PIVGETDATA} to retrieve the Secure Messaging Certificate Signer data object (object identifier \code{0x5FC122}, container identifier \code{0x1017}) and extract the certificate from inner tag \code{0x70}.
  \item Verify that the leftmost eight bytes of the certificate's subjectKeyIdentifier equal the \emph{SM Anchor IIN} reported in \texttt{osdp\_CARDSTATUSR}.
  \item Verify that the certificate's SubjectPublicKeyInfo matches the SubjectPublicKeyInfo stored in the loaded VCI trust anchor record for that IIN.
  \item Verify that the certificate includes the PIV content-signing extended key usage OID (\code{2.16.840.1.101.3.6.7}) or the PIV-I equivalent (\code{2.16.840.1.101.3.8.7}).
  \item Verify that the current time falls within the certificate's validity period (\texttt{notBefore} $\leq$ now $\leq$ \texttt{notAfter}). If the certificate has expired or is not yet valid, the ACU \textbf{SHALL} reject the credential SM session and \textbf{SHALL} unload the corresponding trust anchor.
  \item Perform X.509 path validation and revocation checking in accordance with the deployment's certificate validation policy.
\end{itemize}

PDs \textbf{SHALL} reassemble the complete operation data before processing it. For a load or replacement, the PD \textbf{SHALL} verify that the reassembled \emph{Anchor Data} portion is exactly \emph{Anchor Length} bytes and is a single \code{0x7F50} record before committing it to storage. A successful operation returns \texttt{osdp\_ACK}. Failures return:
\begin{itemize}
  \item \texttt{osdp\_NAK} function-not-supported when the PD does not support trust-anchor caching.
  \item \texttt{osdp\_PIVERROR} \code{0x0005} (invalid parameter) for malformed metadata (unknown operation, reserved bits, invalid lengths, \texttt{MpSizeTotal} not equal to \code{0x000C} plus \emph{Anchor Length}, or a reassembled Anchor Data length not equal to \emph{Anchor Length}).
  \item \texttt{osdp\_PIVERROR} \code{0x0007} (invalid multi-part transfer) when multi-part sequencing fails.
  \item \texttt{osdp\_PIVERROR} \code{0x1021} (insufficient PD memory or storage) when the PD lacks storage space for the anchor.
\end{itemize}

PDs are not required to maintain a real-time clock. PDs may retain either the supplied VCI trust anchor record or an equivalent internal representation so long as the public key and supplied IIN remain available for the verification flow above.

Trust anchors may be stored in volatile or non-volatile memory at the PD’s discretion. Controllers should not assume retention beyond the device’s documented behaviour.

Replacing or deleting the anchor used by an active SM session \textbf{SHALL}
invalidate that session, its VCI state, and PIN-verified status. The PD
\textbf{SHALL} clear security-dependent cached material and trust evidence for
that session. A failed replacement preserves the existing anchor and session.
Changes to unrelated anchors leave the active session unchanged. Trust-store
updates take effect in the next explicitly started preparation attempt.

The reply uses the standard multi-part fields (\texttt{MpSizeTotal}, \texttt{MpOffset}, \texttt{MpFragmentSize}) so PDs can stream the inventory across one or more fragments using reply code \code{0x88} (tentative).
