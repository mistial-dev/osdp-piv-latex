\section{New or Enhanced PIV Commands}

This section introduces commands defined exclusively for the OSDP 3.0 Enhanced PIV profile.

\subsection{PIV Put Data (osdp\_PIVPUTDATA)}

The \texttt{osdp\_PIVPUTDATA} command (command code \code{0xA8}) instructs the PD to deliver an ISO~7816-4 \texttt{PUT DATA} operation to the credential. The ACU \textbf{SHALL} construct the payload as a complete BER-TLV object, including the desired outer tag (\code{0x7E} for the Discovery Object, \code{0x7F61} for a BIT Group Template, \code{0x5C}/\code{0x53} sequences for other data objects, and so on). The PD \textbf{SHALL} forward the payload to the credential using \texttt{CLA = 0x00}, \texttt{INS = 0xDB}, \texttt{P1 = 0x3F}, and \texttt{P2 = 0xFF}. If VCI secure messaging is established, the PD \textbf{SHALL} select the secure channel automatically and adjust the \texttt{CLA} accordingly. Chained APDUs \textbf{SHALL} be generated by the PD when the payload exceeds a single-card APDU.

\input{tables/osdp-pivputdata}

\paragraph{Responses} A successful write is acknowledged with \texttt{osdp\_ACK}. If the PD does not implement the command, it \textbf{SHALL} return \texttt{osdp\_NAK} function-not-supported. When a credential-side failure occurs, the PD \textbf{SHALL} report the failure—either immediately or on a subsequent \texttt{osdp\_POLL}—using \texttt{osdp\_PDERROR} and one of the PIV error codes defined in Subsection~\ref{sec:new-piv-error-codes}: \code{0x1020} when the function is not supported by the credential, \code{0x1021} when the PD lacks buffer space to stage the payload, \code{0x1022} when the credential has insufficient storage, \code{0x1023} when security conditions are not met, or \code{0x1027} when the credential is not present or is removed during the operation. The status word is optional.

\subsection{PIV Application Select (osdp\_PIVSELECT)}

The \texttt{osdp\_PIVSELECT} command (command code \code{0xA7}, tentative) instructs the PD to select the application identified by the supplied Application Identifier (AID) on the currently active credential. The command provides an OSDP-native selector for ISO/IEC~7816-4 \texttt{SELECT by DF name}; it is not a raw APDU tunnel and does not expose APDU header bytes to the ACU. PDs \textbf{SHALL} advertise support via Function Code~12 bit~\code{0x04} (Enhanced PIV) before controllers attempt to use this command.

\input{tables/osdp-pivselect}

The PD \textbf{SHALL} issue \texttt{SELECT} with \texttt{CLA = 0x00}, \texttt{INS = 0xA4}, \texttt{P1 = 0x04}, \texttt{P2 = 0x00}, \texttt{Lc = AID Length}, \texttt{Data = AID}, and \texttt{Le = 0x00}. The PD \textbf{SHALL} request normal FCI return data from the credential and \textbf{SHALL} use the active credential interface selected by the current PIV mode or by the PD's card-present workflow. If VCI secure messaging is established and remains valid for the selected application, the PD \textbf{SHALL} select the secure channel automatically and adjust the \texttt{CLA} accordingly; otherwise changing applications \textbf{SHALL} clear VCI-dependent state, cached pairing codes, and any selected-application metadata derived from the prior application.

The \emph{AID Length} field \textbf{SHALL} be in the ISO/IEC~7816 application identifier range of 5 to 16 bytes. If the payload is malformed, the AID length is outside that range, or any reserved selection flag is nonzero, the PD \textbf{SHALL} report \texttt{osdp\_PDERROR} \code{0x0005}. A successful selection is acknowledged with \texttt{osdp\_ACK}; after success, subsequent PIV commands operate against the selected application until the credential is removed, a new \texttt{osdp\_PIVSELECT} succeeds, or \texttt{osdp\_PIVMODE} changes the operating context. The PD \textbf{SHALL} update the selected AID reported by \texttt{osdp\_CARDSTATUSR}; if the credential returns an FCI template containing tag \code{0x4F}, that value \textbf{SHALL} be reported, otherwise the PD \textbf{SHALL} report the requested AID.

If the PD does not implement the command, it \textbf{SHALL} return \texttt{osdp\_NAK} function-not-supported. Credential-side failures \textbf{SHALL} be reported using \texttt{osdp\_PDERROR}: \code{0x1020} when the credential does not support application selection, \code{0x1023} when security conditions are not satisfied, \code{0x1024} when the requested AID is not present, or \code{0x1027} when the credential is not present or is removed during selection. The status word is optional.

\subsection{Card Status (osdp\_CARDSTATUS)}

The \texttt{osdp\_CARDSTATUS} command (command code \code{0xA9}, tentative) requests the current credential context from the PD. PDs \textbf{SHALL} advertise support via Function Code~12 bit~\code{0x04} (Enhanced PIV) before controllers attempt to use this command. The payload selects the status record that should be returned (currently only the standard profile).

\input{tables/osdp-cardstatus}

PDs \textbf{SHALL} return \texttt{osdp\_NAK} function-not-supported when the command itself is not implemented. If the requested status type is not supported or the payload is malformed, PDs \textbf{SHALL} report the condition via \texttt{osdp\_PDERROR} (for example \code{0x0005} incorrect parameter) on a subsequent \texttt{osdp\_POLL}.

\subsection{Card Status Reply (osdp\_CARDSTATUSR)}

In response to \texttt{osdp\_CARDSTATUS}, the PD reports a ready-to-proceed credential state after completing its card-present workflow (power, application selection, and required reads). PDs \textbf{SHALL NOT} send \texttt{osdp\_CARDSTATUSR} unsolicited on \texttt{osdp\_POLL}. Controllers \textbf{SHOULD} continue to use poll-based \texttt{osdp\_RAW} replies as the single aggregated “card presented and data acquired” indication; PIN usage policy and VCI connectivity \textbf{SHALL NOT} be included in unsolicited poll indications. Detailed readiness (credential type, selected AID, cached data, and readiness flags) \textbf{SHALL} be returned only in solicited \texttt{osdp\_CARDSTATUSR}. When VCI is established, the reply reports both the secure messaging CVC IIN and the loaded anchor IIN used by the PD. These values are identical for direct CVC verification and differ when an Intermediate CVC is used. The PD \textbf{SHALL} set the \emph{VCI Trust Anchor ID} to the identifier assigned in \texttt{osdp\_PIV\_VCILOADTA}; this value \textbf{SHALL} correspond to an entry in the \texttt{osdp\_PIV\_VCITASTATUSR} inventory whose IIN matches the \emph{VCI Anchor IIN} field, so that the ACU can correlate reported VCI state with the anchor management record.

\input{tables/osdp-cardstatusr}

A PD that cannot provide the requested status \textbf{SHALL} return \texttt{osdp\_NAK} when the command is unsupported. For credential-side failures encountered while preparing status, the PD \textbf{MAY} omit \texttt{osdp\_CARDSTATUSR} data and, if available, report details via \texttt{osdp\_PDERROR} on a subsequent \texttt{osdp\_POLL}. Successful replies include the entire selected AID (when available) and the fixed two-byte PIN Usage Policy field after the PD has completed its preparation. When PIN Usage Policy bytes from the credential's Discovery Object (tag \code{0x5F2F}) are available, the PD \textbf{SHALL} report those two bytes verbatim. When no PIV PIN Usage Policy is present or the policy has not yet been read, the PD \textbf{SHALL} report \code{0xFFFF}. The VCI fields describe stable readiness (for example whether a secure channel is established) and the IIN evidence the ACU needs for validation; transient negotiation state \textbf{SHALL NOT} be reported. If the credential is removed before preparation completes, the PD \textbf{MAY} report the condition via \texttt{osdp\_PDERROR} (for example \code{0x1027}) instead of \texttt{osdp\_CARDSTATUSR}. \texttt{osdp\_CARDSTATUSR} is sent only in response to a matching \texttt{osdp\_CARDSTATUS} request.

\subsection{PIV Secure PIN Entry (osdp\_PIVSPE)}

The \texttt{osdp\_PIVSPE} command (command code \code{0xAA}, tentative) instructs the PD to perform an ISO/IEC~7816 \texttt{VERIFY} operation on the credential, allowing the cardholder to enter a PIN directly on the reader. The ACU is responsible for conveying a clear user indication that secure PIN entry is in progress (for example, via displays or annunciators). While \texttt{osdp\_PIVSPE} is active, the PD \textbf{SHALL} suppress all \texttt{osdp\_KEYPAD} reports to the ACU and terminate SPE mode only after returning a result via \texttt{osdp\_PIVSPER}.

\input{tables/osdp-pivspe}

\input{tables/osdp-pivspe-modes}

\input{tables/osdp-pivspe-flags}

Controllers select an \emph{SPE Mode} to match the desired workflow (status query, contact PIN verification, VCI pre-cache/execute, PIN caching, or abort). Modes that rely on VCI (for example \code{0x02} and \code{0x03}) require the PD to have established VCI beforehand. \emph{Start Timeout} and \emph{Inter-key Timeout} values of zero disable the respective timer. \emph{Cache Validity} is expressed in seconds (LSB first); a value of zero disables PIN caching. If a mode requests PIN caching, the PD \textbf{SHALL NOT} transmit the PIN to the ACU.

Each \texttt{osdp\_PIVSPE} command that selects a PIN-entry mode initiates exactly one PIN-entry session. Status-only and clear/abort modes do not initiate PIN entry; they report or clear PD state and then terminate. When the PD returns \texttt{osdp\_PIVSPER} for a PIN-entry mode, the SPE session terminates unconditionally, including on PIN mismatch, regardless of whether the credential remains present. The ACU \textbf{MAY} re-issue \texttt{osdp\_PIVSPE} to permit an additional attempt; it \textbf{SHOULD} use the \emph{Attempts Remaining} count from the preceding \texttt{osdp\_PIVSPER} to inform its retry policy.

A successful request is acknowledged with \texttt{osdp\_ACK}. If the PD does not implement the command, it \textbf{SHALL} return \texttt{osdp\_NAK} function-not-supported. Credential-side outcomes (for example credential removal, incorrect parameters, security status not satisfied, or VCI not established) \textbf{SHALL} be reported in the subsequent \texttt{osdp\_PIVSPER} result code per Table~\ref{tab:pivsper-results}. After issuing \texttt{osdp\_PIVSPE}, the ACU \textbf{SHALL NOT} send other PIV commands until a corresponding \texttt{osdp\_PIVSPER} reply is received.

\subsection{PIV Biometric Match (osdp\_PIVBIOMATCH)}

The \texttt{osdp\_PIVBIOMATCH} command (command code \code{0xAB}, tentative) instructs the PD to acquire a live sample and compare it to the specified biometric template from the active application. Depending on the \emph{Match Mode}, the comparison occurs either on the credential (on-card match) or within the PD (off-card match).

\input{tables/osdp-pivbiomatch}

\input{tables/osdp-pivbiomatch-types}

Controllers set \emph{Match Mode} to select off-card or on-card comparison. Off-card flows require the PD to retrieve the appropriate template and, where applicable (e.g., TWIC contactless), to have a valid privacy key loaded via \texttt{osdp\_PIV\_LOADTPK}. On-card flows require the credential to support OCC. If the PD does not implement the command, it \textbf{SHALL} return \texttt{osdp\_NAK} function-not-supported. Credential-side match outcomes (for example PIN verification required or credential removal during operation) \textbf{SHALL} be reported in the subsequent \texttt{osdp\_PIVBIOMATCHR} result code per Table~\ref{tab:pivbiomatch-results}. Conditions that prevent the command from being attempted (for example unsupported credential function, missing VCI when required, or invalid command parameters) \textbf{MAY} be reported via \texttt{osdp\_PDERROR} on a subsequent \texttt{osdp\_POLL}.

\subsection{PIV Biometric Match Reply (osdp\_PIVBIOMATCHR)}

After \texttt{osdp\_PIVBIOMATCH} completes, the PD reports the result as a poll response using reply code \code{0x87} (tentative).

\input{tables/osdp-pivbiomatchr}

When \emph{Result} is \code{0x00} (off-card match success), the PD \textbf{SHALL} include the 32-byte SHA-256 hash of the biometric template tag \code{0xBC} data field in the reply. For on-card match success (\emph{Result} \code{0x09}) and for all failure result codes, the PD \textbf{SHALL} omit the hash field; ACUs \textbf{SHALL NOT} rely on a hash received alongside any result other than \code{0x00}.

Off-card biometric comparison demonstrates only that the live sample matched template data presented to the PD. Because off-card biometric objects can be copied or duplicated, an off-card biometric match does not by itself prove authenticity of the credential. On-card biometric comparison is a credential-controlled assertion; the biometric object may be attacker controlled and the PD does not receive the template data being matched. To obtain cryptographic proof associated with an on-card biometric success, the ACU \textbf{SHALL} perform an additional authentication using an appropriately verified credential key after the successful on-card comparison.

\subsection{TWIC Privacy Key Load (osdp\_PIV\_LOADTPK)}

The \texttt{osdp\_PIV\_LOADTPK} command (command code \code{0xAC}, tentative) instructs the PD to cache a TWIC Privacy Key (TPK) for use with subsequent biometric operations against a TWIC credential. Function Code~14 is the biometric-support compliance byte; before using this command, controllers \textbf{SHOULD} verify that Function Code~14 advertises the OSDP~3.0 biometric command set and the relevant biometric modality bits for the intended TWIC operation.

\input{tables/osdp-loadtpk}

Controllers set \emph{Cache Timeout} to define how long (in seconds) the PD may retain the key. A value of \code{0x00} clears any cached TPK immediately. Values \code{0x01}-\code{0xFF} allow caching for up to 255 seconds. Bit~0 of \emph{Control Flags} directs the PD to clear the cached TPK when the credential is removed; all other bits are reserved and \textbf{SHALL} be transmitted as zero. If the PD does not support TWIC TPK caching it \textbf{SHALL} return \texttt{osdp\_NAK} function-not-supported. Invalid payloads (for example reserved bits set) \textbf{SHALL} elicit \texttt{osdp\_PDERROR} \code{0x0005}.

\subsection{PIV VCI Pairing Code Transmit (osdp\_PIV\_XMITPAIRING)}

The \texttt{osdp\_PIV\_XMITPAIRING} command (command code \code{0xAD}, tentative) delivers an eight-digit pairing code to the PD for use during Virtual Contact Interface (VCI) establishment. The pairing code is transmitted from the ACU to the PD only over OSDP Secure Channel~2.0, and is used by the PD to establish VCI secure messaging with the credential. Controllers \textbf{SHALL NOT} issue this command unless a PIV application is currently selected and VCI mode is active.

\input{tables/osdp-xmitpairing}

The pairing code is encoded as eight ASCII digits (\texttt{'0'}-\texttt{'9'}). If no PIV application is selected, the PD \textbf{SHALL} return \texttt{osdp\_PDERROR} \code{0x0005}. Otherwise, the PD \textbf{SHALL} cache the pairing code only as an input to VCI establishment for the currently selected PIV application and use it when required by the credential’s Discovery Object PIN Usage Policy (for example when bit~4 is set and bit~3 is clear in the first byte). The pairing code is not evidence that VCI secure messaging is already established, and \texttt{osdp\_PIV\_XMITPAIRING} is not transported over VCI secure messaging. When VCI secure messaging is already active or the credential does not require pairing to establish VCI, the PD \textbf{MAY} ignore the supplied code after acknowledging receipt. PDs \textbf{SHALL} clear any stored pairing code when VCI is established, when VCI is torn down, or when the active PIV mode changes.

\paragraph{VCI security preconditions}
VCI trust-anchor load/status, VCI pairing-code transmit, VCI establishment, and PIV operations that depend on VCI \textbf{SHALL} be accepted only when OSDP Secure Channel 2.0 is active between the ACU and PD. This OSDP Secure Channel protects ACU-to-PD management traffic, including \texttt{osdp\_PIV\_XMITPAIRING}; VCI secure messaging is the separate PD-to-credential secure channel established by the PD. A PD \textbf{SHALL} reject VCI-related functionality when operating with factory/default SCBK or other factory keys. Security-precondition failures \textbf{SHALL} be reported using \texttt{osdp\_PDERROR} \code{0x0006} where the command supports \texttt{osdp\_PDERROR}; otherwise the command’s existing failure reporting path applies.

\subsection{Set PIV Mode (osdp\_PIVMODE)}\label{sec:pivmode}

The \texttt{osdp\_PIVMODE} command (command code \code{0xAE}, tentative) defines the operating context for PIV, TWIC, and related credential transactions. OSDP~3.0 replaces the OSDP~2.2 “Application + AID” fields with a configuration payload that includes a required Global Interface Mask byte, PIV Auto challenge parameters when autonomous operation is enabled, and a TLV list of configuration descriptors so controllers can specify multiple application profiles, preferred interfaces, and optional Application Identifiers. PDs \textbf{SHALL} advertise support via Function Code~12 bit~\code{0x04} (Enhanced PIV).

\input{tables/osdp-pivmode}

The \emph{PIV Mode Flags} byte enables global behaviours such as autonomous operation and VCI usage (Table~\ref{tab:pivmode-flags}). Bits not listed remain reserved and \textbf{SHALL} be transmitted as zero.

\input{tables/osdp-pivmode-flags}

Global and per-entry interface masks use the bit positions in Table~\ref{tab:pivmode-interfaces}; the Global Interface Mask bounds the interfaces a PD may use when processing all configuration entries.

\input{tables/osdp-pivmode-interfaces}

After the flags, the payload uses standard multi-part framing fields and a configuration count (1-32). The count is followed by the required Global Interface Mask byte. If and only if PIV Auto is enabled in \emph{PIV Mode Flags}, the Global Interface Mask is followed by the Series Counter, Sequence Counter, and fixed 32-byte Supplemental Entropy field before the TLV list. When PIV Auto is not enabled, those three conditional fields are absent and the TLV list begins immediately after the Global Interface Mask. Each configuration appears as a TLV:

\begin{itemize}
  \item \textbf{Global Interface Mask (required)} — One-byte mask (no tag) that limits the interfaces the PD may use for all configurations (see Table~\ref{tab:pivmode-interfaces}). A value of \code{0x00} indicates no global restriction; reserved bits \textbf{SHALL} be zero.
  \item \textbf{Configuration Entry (Tag \code{0x01})} — Contains the data-model identifier, a per-entry interface mask, the AID length, and the optional AID:
    \begin{itemize}
      \item \emph{Data Model} (\code{0x01} PIV, \code{0x02} TWIC, \code{0x03} CAC, values \code{0x04}-\code{0x7F} reserved, \code{0x80}-\code{0xFF} private use). CAC entries use the same interface and AID encoding as PIV and TWIC entries.
      \item \emph{Interface Mask} — Uses the same bit positions as the global mask (Table~\ref{tab:pivmode-interfaces}) and \textbf{SHALL NOT} assert interfaces excluded by the Global Interface Mask. A value of \code{0x00} means “any interface permitted by the global mask.”
      \item \emph{AID Length} (0-16) and \emph{AID} bytes when provided.
    \end{itemize}
\end{itemize}

PDs process configuration entries in order, applying the global mask (when present) before honouring each entry’s mask. Invalid masks, unknown data-model identifiers, or malformed TLVs \textbf{SHALL} result in \texttt{osdp\_PDERROR} \code{0x0005}. Controllers \textbf{SHALL} send the command over a secure channel where required; the PD \textbf{SHALL} return \texttt{osdp\_PDERROR} \code{0x0006} if the necessary security conditions are not satisfied. Multi-part framing errors result in \texttt{osdp\_PDERROR} \code{0x0007}. If the PD cannot cache the requested configuration set, it \textbf{SHALL} respond with \texttt{osdp\_PDERROR} \code{0x1021}.

When PIV Auto is enabled, PDs interrogate the credential on presentation, establish VCI automatically when possible, derive the PIV Auto challenge, issue the PIV GENERAL AUTHENTICATE command, and report the signed response without additional ACU prompts. If a pairing code is required, the PD signals the state change via a solicited \texttt{osdp\_CARDSTATUSR} (not via unsolicited poll); the ACU then provides the code using \texttt{osdp\_PIV\_XMITPAIRING} over OSDP Secure Channel~2.0, and the PD uses the code to complete VCI establishment.

PIV Auto configuration \textbf{SHALL} be accepted only when OSDP Secure Channel~2.0 is active and the channel is not using a factory/default SCBK or other factory key material. A PD \textbf{SHALL} reject PIV Auto configuration or execution with \texttt{osdp\_PDERROR} \code{0x0006} when these preconditions are not met.

When bit \code{0x01} of \emph{PIV Mode Flags} enables PIV Auto, the configuration \textbf{SHALL} specify a \emph{Series Counter}, a \emph{Sequence Counter}, and a 32-byte \emph{Supplemental Entropy} field. The supplemental entropy field is fixed width and \textbf{SHALL} always be present; all zeroes are permitted for compatibility but are not recommended. The ACU \textbf{SHALL} ensure that a series counter value does not repeat for the same PD and that no sequence counter value is issued more than once within a series. One conforming implementation strategy is to maintain a monotonic series counter that increments at every ACU boot, similar to the SNMP engine boots counter, and a monotonic sequence counter for challenges issued within that boot series.

The PIV Auto challenge \textbf{SHALL} be derived from the active Secure
Channel~2.0 session key material using two KMAC256 operations. First, the PD
derives a 32-byte PIV Auto KDK with key material formed by concatenating
\code{S-ENC}, \code{S-MAC1}, and \code{S-MAC2}; empty input data; output length
32 bytes; and customization string \code{OSDP-PIV-AUTO-KDK-v1}. Second, the PD
derives the challenge digest using the PIV Auto KDK as the KMAC key, the
fixed-width template as input data, output length \code{L}, and customization
string \code{OSDP-PIV-AUTO-CHALLENGE-v1}. The fixed-width template
\textbf{SHALL} contain the series counter, sequence counter, credential
FASC-N, credential UUID, challenged PIV key reference, PIV algorithm
identifier, and the 32-byte supplemental entropy field. A successful PIV Auto
transaction \textbf{SHALL} include the credential UUID; if the UUID cannot be
read, the PD \textbf{SHALL} report PIV Auto failure instead of deriving a
success challenge with an all-zero UUID. The output length \code{L} is 32 bytes
for SHA-256 profiles and 48 bytes for SHA-384 profiles. PIV Auto challenge
derivation \textbf{SHALL NOT} use static factory keys.

The first \texttt{osdp\_POLL} response after completion \textbf{SHALL} contain \texttt{osdp\_PIVSTATUSR}; subsequent fragments, when required, \textbf{SHALL} use the same reply and advance \emph{MpOffset} until the complete status payload is delivered.

\input{tables/osdp-pivstatusr}

Result and detail codes follow Table~\ref{tab:pivstatusr-results}. When \emph{Result} is \code{0x00}, \emph{Detail} is reserved and \textbf{SHALL} be \code{0x00}. When \emph{Result} is not \code{0x00}, the PD \textbf{SHALL} set \emph{Signed Response Length} to \code{0x0000} unless a credential response was received and is useful for ACU diagnostics.

\input{tables/osdp-pivstatusr-results}

The reply reports the exact series and sequence counters used for the challenge, the FASC-N and UUID read from the credential, and the signed response returned by the credential. multi-part convention. \emph{MpSizeTotal} is the total status payload size,
\emph{MpOffset} is the zero-based offset of the fragment, and
\emph{MpFragmentSize} is the number of payload bytes carried in that fragment.

contiguous bytes of the signed response.

\subsection{VCI Trust Anchor Load (osdp\_PIV\_VCILOADTA)}

The \texttt{osdp\_PIV\_VCILOADTA} command (command code \code{0xAF}, tentative) loads, replaces, or deletes a Virtual Contact Interface (VCI) trust anchor. The ACU \textbf{SHALL} validate and authorize each trust anchor under its deployment certificate policy before loading it. Trust anchors must be cached before a PD can verify card certificates during VCI establishment.

\input{tables/osdp-vciloatda}

The metadata block (operation, identifier, IIN, anchor length) appears only in the first fragment where \texttt{MpOffset = 0}; subsequent fragments carry additional anchor bytes. Controllers set \emph{Operation} to \code{0x00} to load or replace the anchor identified by \emph{Trust Anchor ID}. Set \emph{Operation} to \code{0x01} with \emph{Anchor Length} \code{0x0000} to delete the anchor. Inventory is requested with \texttt{osdp\_PIV\_VCITASTATUS}, not with \texttt{osdp\_PIV\_VCILOADTA}. The \emph{Issuer Identifier Number (IIN)} is an OSDP-defined anchor selector: it \textbf{SHALL} be the leftmost eight bytes of the subjectKeyIdentifier from the content-signing X.509 certificate associated with this anchor. This value \textbf{SHALL} match the IIN field (tag \code{0x42}) in the VCI trust anchor record.

The \emph{Anchor Length} declares the exact total size of the variable-length VCI trust anchor record. For load operations, \texttt{MpSizeTotal} \textbf{SHALL} equal \emph{Anchor Length}, the sum of all accepted fragment lengths \textbf{SHALL} equal \emph{Anchor Length}, and no fragment \textbf{SHALL} extend beyond \emph{Anchor Length}. A conforming VCI trust anchor record \textbf{SHALL NOT} exceed 576 bytes (\code{0x0240}). The PD \textbf{SHALL} accept any valid record length from the minimum BER-TLV encoding through \code{0x0240}, subject to supported-key and storage-capacity checks.

PD storage accounting for VCI trust anchors is variable-length. A PD \textbf{SHALL NOT} treat every anchor as consuming the maximum \code{0x0240} bytes unless that is the PD's documented physical allocation model. When reporting capacity, loading, replacing, or deleting anchors, the PD \textbf{SHALL} account for stored anchors by their actual \emph{Anchor Length} values and \textbf{SHALL} use the same accounting rule for both \texttt{osdp\_PIV\_VCITASTATUSR} \emph{Available Bytes} and \texttt{osdp\_PIV\_VCILOADTA} storage acceptance. A replacement operation \textbf{SHALL} be evaluated after releasing the storage occupied by the existing anchor with the same \emph{Trust Anchor ID}; if the replacement cannot be completed, the prior anchor \textbf{SHALL} remain available. A delete operation \textbf{SHALL} release the storage associated with the deleted anchor.

\end{SimpleTable}

The VCI trust anchor record is intentionally not a NIST SP~800-73 Intermediate CVC and does not carry X.509 path-validation state. The ACU is responsible for selecting, loading, unloading, and validating the VCI anchors it permits a PD to use before the PD relies on them. The PD uses the record only as a local public-key verifier selected by IIN. The maximum record size is derived from the largest supported key case: a 550-byte RSA-4096 SubjectPublicKeyInfo plus the fixed fields above and BER-TLV length overhead. The resulting worst case is 573 bytes; this specification rounds the maximum accepted record size to 576 bytes.

\paragraph{Use during VCI establishment}
When the PD receives the secure messaging CVC from the credential, it \textbf{SHALL} first extract the Issuer Identification Number from tag \code{0x42}. If a loaded VCI trust anchor has a matching IIN, the PD \textbf{SHALL} use that anchor's SubjectPublicKeyInfo to verify the secure messaging CVC signature. If verification succeeds, the PD may continue VCI establishment using the public key in the secure messaging CVC.

If no loaded VCI trust anchor matches the secure messaging CVC IIN, the PD \textbf{SHALL} retrieve the Secure Messaging Certificate Signer data object (PIV data object \code{0x1017}, tag \texttt{5FC122}) from the credential and inspect it for one Intermediate CVC (tag \code{0x7F21}). If the object is absent or no Intermediate CVC is present, validation fails. If an Intermediate CVC is present, the PD \textbf{SHALL} verify all of the following before continuing:
\begin{itemize}
  \item The secure messaging CVC IIN (tag \code{0x42}) equals the Subject Identifier (tag \code{0x5F20}) in the Intermediate CVC.
  \item The Intermediate CVC Role Identifier (tag \code{0x5F4C}) is \code{0x12}.
  \item A loaded VCI trust anchor exists whose IIN equals the Intermediate CVC IIN (tag \code{0x42}).
  \item The Intermediate CVC signature verifies using the matching VCI trust anchor public key.
  \item The secure messaging CVC signature verifies using the public key carried in the Intermediate CVC.
\end{itemize}

The PD validates only the CVC chain needed for VCI establishment: either the loaded trust anchor directly verifies the secure messaging CVC, or the loaded trust anchor verifies the Intermediate CVC that then verifies the secure messaging CVC. The PD \textbf{SHALL NOT} establish VCI unless this CVC validation succeeds. The PD \textbf{SHALL NOT} perform full X.509 path validation, validity-period evaluation, certificate-policy evaluation, or revocation processing for VCI trust anchors; those checks are completed by the ACU before loading anchors and again as an acceptance policy after VCI state is reported.

\paragraph{ACU post-VCI validation}
After receiving \texttt{osdp\_CARDSTATUSR} with VCI established, the ACU \textbf{SHALL} validate the content-signing certificate corresponding to the reported \emph{VCI Anchor IIN} before treating the VCI session as accepted for the deployment. This validation is an additional ACU acceptance check and does not replace the PD's required CVC validation during VCI establishment. The ACU \textbf{SHALL} perform all of the following:
\begin{itemize}
  \item Obtain the content-signing X.509 certificate. If the ACU does not already possess a cached copy whose subjectKeyIdentifier leftmost-eight-bytes equals the \emph{VCI Anchor IIN}, the ACU \textbf{SHALL} use \texttt{osdp\_PIVDATA} to retrieve the Secure Messaging Certificate Signer data object (PIV data object \code{0x1017}, tag \texttt{5FC122}) and extract the certificate from inner tag \code{0x70}.
  \item Verify that the leftmost eight bytes of the certificate's subjectKeyIdentifier equal the \emph{VCI Anchor IIN} reported in \texttt{osdp\_CARDSTATUSR}.
  \item Verify that the certificate's SubjectPublicKeyInfo matches the SubjectPublicKeyInfo stored in the loaded VCI trust anchor record for that IIN.
  \item Verify that the certificate includes the PIV content-signing extended key usage OID (\code{2.16.840.1.101.3.6.7}) or the PIV-I equivalent (\code{2.16.840.1.101.3.8.7}).
  \item Verify that the current time falls within the certificate's validity period (\texttt{notBefore} $\leq$ now $\leq$ \texttt{notAfter}). If the certificate has expired or is not yet valid, the ACU \textbf{SHALL} reject the VCI session and \textbf{SHALL} unload the corresponding trust anchor.
  \item Perform X.509 path validation and revocation checking in accordance with the deployment's certificate validation policy.
\end{itemize}

PDs \textbf{SHALL} reconstruct the anchor from the fragments before storing it. The PD \textbf{SHALL} verify that the reconstructed byte string is exactly \emph{Anchor Length} bytes and is a single \code{0x7F50} record before committing it to storage. A successful operation returns \texttt{osdp\_ACK}. Failures return:
\begin{itemize}
  \item \texttt{osdp\_NAK} function-not-supported when the PD does not support trust-anchor caching.
  \item \texttt{osdp\_PDERROR} \code{0x0005} for malformed metadata (unknown operation, reserved bits, invalid lengths, \texttt{MpSizeTotal} not equal to \emph{Anchor Length}, or a fragment range outside \emph{Anchor Length}).
  \item \texttt{osdp\_PDERROR} \code{0x0007} when multi-part sequencing fails.
  \item \texttt{osdp\_PDERROR} \code{0x1021} when the PD lacks storage space for the anchor.
\end{itemize}

PDs are not required to maintain a real-time clock. PDs may retain either the supplied VCI trust anchor record or an equivalent internal representation so long as the public key and supplied IIN remain available for the verification flow above.

Trust anchors may be stored in volatile or non-volatile memory at the PD’s discretion. Controllers should not assume retention beyond the device’s documented behaviour.

The \texttt{osdp\_PIV\_VCITASTATUS} command (command code \code{0xA6}, tentative) enumerates cached trust anchors and reports remaining storage capacity. The request carries no payload.
